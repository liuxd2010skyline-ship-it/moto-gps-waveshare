## 1. 本轮已完成的工作

- 设计颜色集中到 `shared/nav_ui/assets/nav_design_palette.json`，共 31 个色值；生成器同时输出固件头文件和浏览器色板。生成文件禁止独立改色。
- 导航页修正底色、路线深衬、建筑暗边、位置箭头暗边、单位、限速牌与进度弧的代码色差。其他页面的原石墨色单独保留。
- 电脑预览直接显示真彩设计色。已否决的蓝/青聚光方案和 RGB565 对照不再成为预览中的配色选项。
- 漫反射改为随机出生、漂移、消失，数量不固定且最多 4 组。出生位置与寿命在出生时抽样，逐帧位置和透明度连续，总 opacity 上限 1.9。
- 完整/有限/道路/仅路线场景共用同一光场，切换地物密度不重启相位；真实导航事件才触发一次微弱反馈。
- 修复原生 SVG 预览仍按“固定三组”查找节点的问题；现在两种浏览器入口都能处理光斑出生与死亡。
- 本地浏览器核查滑杆、暂停、完整地物融合、路线像素色值及 128 帧动画；主 HUD 在全部帧中保持像素一致。提供真彩动画 PNG，避免用 GIF 的 256 色评价渐变。
- 本地重新编译真实 LVGL 导航代码，原生 9/9 测试通过。CI 加入设计状态/运动测试与色板生成一致性检查。
- 底图窗口的 GCJ-02 中心与半径现在沿 BLE → NavSnapshot → NavPresenter 保留。车辆超出已收到窗口时，道路和建筑一起撤下；同一区域换路线不误删有效地物。新增真实桥接回归覆盖海淀路线误收到济南窗口、越界、无效范围、断连及版本回绕。
- 场景版本改为 UInt32 序列比较，允许 `0xFFFFFFFE → 1` 正常更新，重复和迟到的旧窗口仍被拒绝。

**上述硬件代码变更主要是色板接入。随机柔光和完整场景选择器还没有进入固件运行时。**

## 4. 底图问题单独闭环

保留手机原路线预览与电动自行车功能；修复重点在圆屏数据链路和共享绘图。`AppModel.swift` 真实导航不调用 `surroundingMap.update`，其加载器明确是 `example.invalid` 占位并返回 unsupportedURL。`MapScene` 绘图层存在，但目前没有收到海淀真实道路/建筑。仓库原后端包含 OSM/Protomaps 网关，它与既定“不运行常驻网关、使用中国数据提供方”目标不一致，不能擅自重新开启。

| 底图问题 | 已有基础 | 下一步实际处理及验收 |
| --- | --- | --- |
| 数据源缺失 | 有规范化 GCJ-02 TileDocument 和 MapScene | 取得海淀正式道路/轮廓样本，核对字段/覆盖，再接入 source adapter；没有样本时只绘真实路线 |
| 演示数据串入实地 | demo 已隔离，reset 会发空场景替换 | 演示→实地、停止→新路线、断连→重连均检查旧地物清理；禁止济南样例进入海淀真实模式 |
| 坐标偏移或二次转换 | 核心与 MapScene 使用 GCJ-02；WGS84 瓦片规划有边界转换 | 对每个数据源声明坐标类型，只在来源边界转换一次；用同一真实道路/路线控制点核验 BD-09/WGS84/GCJ-02 处理 |
| 建筑太少、被截断 | 16 栋/128 点的完整替换窗口，24 条/192 点道路 | 优先屏内相关地物、保形简化与连续场景缓存；达到上限不硬切断建筑多边形。若目标需要更多轮廓，整体评估协议、索引、内存、BLE 带宽再扩容 |
| 不规则建筑被画成方块 | 原生已有真实多边形三角化 | 只保留源轮廓；有足够点才绘制；处理凹多边形、自交、极小形体与重复闭合点，不生成填空建筑 |
| 道路错接、桥隧误读 | 每条道路独立 span，基本分级存在 | 保留道路分段与层级，跨瓦片边缘统一坐标、去重；不连成一条人为长线 |
| 图层位置不同步 | 路线/道路/建筑共用一个投影和车辆锚点 | 同一窗口、同一时刻、同一坐标系统；任何平移/缩放/航向处理同时应用所有真实图层 |
| 旧场景迟到覆盖新场景 | iOS generation 取消旧任务；BLE scene_revision 已支持回绕并拒绝旧窗口；本轮把中心/半径送到绘图端，车辆越界撤下两层 | 仍需局部覆盖语义和窗口边缘淡入。本轮只验证车辆锚点在窗口内，不能由此声称整个可见圆盘都有数据；地图是地理窗口，不必无故绑定某条路线 |
| 局部缺口和缓存失败 | 已有瓦片缓存、配额、失败退避 | 明确区分空地/无建筑/未知覆盖，保留可信局部图层；未知区域柔和留白；光场不伪装地理信息 |
| 与路线叠加后的灰阶层次 | 原生基本灰阶和本轮统一色板 | 保持底色 < 建筑 < 道路 < 白线/HUD；材质微渐变、短渐隐、窄暗边按同一设计稿校准 |

数据源审查的依据为 [海淀核查记录](../docs/BEIJING_HAIDIAN_MAP_SOURCE_REVIEW.md)，其中没有已证实可直接使用的正式细粒度接口。这里不虚构一个“地图 API 已接通”的结果，也不通过装饰层补画不存在的街区。

## 6. 完成顺序及每步验收

1. **统一契约与状态选择器**：将新鲜定位、几何匹配、动作身份和限速有效性送到 UI；原子决定可见层。验收定位失效/重算/断连/版本不一致时没有旧白线、旧数字或旧限速指导。
2. **底图源及规范化管线**：以海淀真实样本验证 source adapter、坐标转换、保形裁剪、优先级选择、跨瓦片去重与场景缓存；保持手机原预览不变。真实源缺失时完成可接入契约与仅路线输出，明确缺口。
3. **B 视觉细节统一**：保留 V6 图形，落实英文 HUD、实际字宽排版、数字粗细、渐隐曲线/层序、进度弧、道路微渐变、建筑灰阶与窄边缘。用有牌/无牌及 80 m、300 m、1.2 km、四位数字逐屏对照。
4. **柔光进入真实 LVGL**：生成低成本软边 mask、固定空间抖动、随机生命周期与事件控制器；同一背景可叠加真实完整底图。目标 2 Hz，导航和 IMU 更新优先，不增加全屏 RGB565 缓冲。
5. **补齐情境与数据附件**：近转弯镜头、连续动作、桥隧层级、局部覆盖与历史图层按可靠数据逐项开启；没有证据的附件保持隐藏。
6. **构建与实机总验收**：色板/行为检查→9 项及新增契约回归→ESP-IDF 固件→对应 artifact→466 px 室内/户外实屏→海淀短路线/重算/断连实测。只有实际进入固件并通过对应测试的项目才能标“完成”。
